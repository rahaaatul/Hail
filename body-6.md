**Accept** — `c9db804`. You are right that I fixed the *whether* and left the *what*, and that the leftover is a trap rather than a failure: the frozen `dir` is invisible from inside a class that only reads `const val`s.

`filesDirThatOutlivesThisClass()` is one directory under the system temp dir, created with `mkdirs()` and never deleted. The `TemporaryFolder` rule is gone, so nothing this class installs disappears before the next test runs, and the comment says why: `HailData.dir` is a plain `val` built from `app.filesDir`, the first touch in the JVM freezes it, and a later `setUp` cannot move it — so the path has to be stable for the JVM's lifetime, not the test's.

Worth noting what the fix does *not* try to do. It does not restore the previous value in `@After`, because there is no previous value to restore: `HailData` is a singleton, `setAppForTest` has a private setter, and `mockkObject` does not reset statics. A test class that wants a different `filesDir` has to be the one that installs it before `HailData` is touched, which is a property of the suite rather than something this class can hand over. The honest version of that is what you asked for — a directory consistent with what the rest of the suite installs, outliving the class.
