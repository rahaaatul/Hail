Right on both counts: nothing tied a literal range to the map, so a slider could be narrower than the declaration and the failure would be silent and deferred — the user picks `12` for a range the map says is `11f..16f`, and every later restore of that setting quietly leaves it alone, warning to HLog and nothing to the person watching the screen. On a clean install that is also the default value, so the first restore of a fresh backup looks like it worked.

`every slider binds its range and default to the declared float preference` walks the real `sliderPreference(` call sites in `src/main/kotlin`, requires the `key` argument to be a `HailData` constant, and requires `valueRange` and `defaultValue` to both resolve to that constant in `HailData`. So `12f..16f` fails, `11f..16f` with `16f` as the default fails, and a `Float` key with no slider at all does not fail — a key the screen never offers can still be restored.

Blanket on purpose, and worth naming rather than leaving implied: every slider in this app is a Float slider today, and an Int or Long slider would fail this check. That is the day the check has to be taught the difference, and it should be a deliberate change to this test rather than a slider somebody adds and a `contains` that quietly stops matching.
